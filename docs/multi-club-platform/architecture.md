### 2.3. Почему весь список ID календаря не равен участникам

В полной таблице 11 именованных участников, но действующий парсер полного календаря получает **14 ID, 22 тура, 113 записей матчей**. Дополнительные ID — `1029`, `258`, `0`: в соответствующих карточках нет названий и эмблем. Они присутствуют и в исходном JSON. На момент проверки найдены 13 записей календаря с участием хотя бы одного такого ID.

Это не основание объявлять три новых клуба или приписывать название из старой новости. В будущей модели:

- `participantTeamIds` содержит 11 подтверждённых участников из полной сезонной таблицы;
- исходные матчи и неизвестные ID сохраняются в слое исходных данных/истории;
- неразрешённая сторона имеет `sourceTeamId` и причину `identity_not_confirmed`, без вымышленной клубной страницы;
- историческая дата без результата не становится подтверждённым будущим матчем;
- снятие, замена команды или аннулирование результатов требуют отдельного официального подтверждения. Пустые поля его не заменяют.

## 3. Источники и доступность данных

### 3.1. Обозначения и ограничения проверки

**П** — данные опубликованы и прочитаны непосредственно у источника в день аудита с проверкой указанного контекста. Это наличие на момент получения, без обещания редакционного обновления в реальном времени. **С** — опубликованы ранее, актуальность не подтверждена. **Н** — поле/публикации отсутствуют в проверенном корректном разделе. **В** — источник временно недоступен, новое значение определить нельзя. Сетевую ошибку нельзя записывать как Н.

Количество строк состава получено из `.team_data_content > .team_data_players`, без тренеров/представителей. Это опубликованный клубный список, а не гарантия текущего допуска всех игроков к сезону: регистрацию и сезон нужно проверять по профилю. Всего прочитаны 402 записи составов; это не число уникальных футболистов. Полная индивидуальная статистика всех этих записей на первом этапе не проверялась.

Найденный [материал КДК](https://rffk-roo.ru/news/2124/) по содержанию относится к 2022 году и исключён из данных 2026 независимо от даты поискового индекса.

### 3.4. Выявленные противоречия и частота обновления

1. **Краткая таблица отстаёт от полной.** В полученной сезонной странице краткий блок показывал у Каштана 16 игр и 48 очков, полный раздел — 17 и 51. Нельзя разбирать весь текст как одну таблицу. Для новой модели приоритет у полного закреплённого раздела; конфликт фиксируется без усреднения и без незаметной перезаписи старой таблицы.
2. **Рейтинг может суммировать разные клубы.** [Барканов, 1698](https://rffk-roo.ru/players/1698/), подписан УОР: 10 игр, 7 голов, 782 минуты в рейтинге. Профиль 2026/2026 разделяет УОР — 5 игр, 1 гол, 337 минут; «Саки» — 5 игр, 6 голов, 445 минут. Нельзя приписать все показатели УОР или ограничивать суммарные игры числом матчей только УОР. Хранить клубные строки отдельно от общего рейтинга.
3. **Состав не равен сезонной статистике.** У [3516](https://rffk-roo.ru/players/3516/) есть регистрация УОР, но нет сезонной строки. Его игры/голы/минуты остаются неизвестными. «Игр» в составе может охватывать другие сезоны; существующий код выделяет это как `federation_games`.
4. **SLA РФФК не подтверждён.** В изученных страницах не опубликованы гарантированный интервал обновления, документация публичного API или метка версии каждого набора. HTML доступен без входа; приложение использует HTML, а не документированный API. Live-счёт или ежеминутное подтверждение составов обещать нельзя.

Текущий цикл проекта: Actions — `0 * * * *`; PWA получает опубликованный JSON каждые пять минут, при фокусе, возврате вкладки и восстановлении сети. Это частота нашего получения, не публикации РФФК. Сохранять расписание; общие страницы турнира загружать один раз за цикл, не 11 раз. Для сотен профилей нужны кэш, очередь повторов, бюджет времени и ограничение параллельности — стартово не выше существующих четырёх запросов одновременно, с измерением нагрузки перед включением.

## 4. Существующая архитектура

### 4.1. Клиент, стили и маршруты

Это статическая buildless PWA: `index.html` содержит разметку, встроенные CSS и обычный JavaScript без фреймворка. `modern-home.css`, `match-center.css`, `championship.css` существуют отдельно, но исполняемый HTML также содержит встроенные стили. Изменение только отдельного CSS не гарантирует изменение страницы; способ синхронизации нужно учитывать. `apply_visual_refresh.py` — инструмент прежней миграции оформления, не обязательная текущая сборка.

Основные разделы: `home`, `matches`, `table`, `squad`, `news`; дополнительные — `player`, `match`. Внизу пять утверждённых кнопок. Чемпионат уже включает таблицу, туры/матчи и бомбардиров. `renderHome`, `renderSquad`, `renderPlayer`, `renderMatch`, `renderChampionship` работают в одном документе.

Hash-маршруты: `#home`, `#matches`, `#table`, `#squad&role=…`, `#news`, `#player=…`, `#match=…`. `currentRoute`, `routeParent`, `applyRoute`, `rememberPosition`, `returnToParent` сохраняют контекст, scroll/фокус через History API. Есть `popstate`/`hashchange`, стандартные модифицированные клики по ссылкам. Ключ профиля — `rffk-<playerId>` из URL РФФК, с legacy-вариантом при отсутствии ID. Чужие профили пока обычно открываются на РФФК; встроенный центр матча ориентирован на «Судак».

В UI и парсерах зашиты `TEAM=141`, название «Судак», ориентация счёта «наши/чужие», эмблема, отбор профилей и сопоставление таблицы по имени. Переключать эти глобальные переменные ради другого клуба опасно: нужен явный контекст и адаптер совместимости.

### 4.3. PWA, состояние и Pages

- `manifest.json`: один scope `.`, start URL `.`, standalone, отдельные any/maskable-иконки из `assets/pwa-launcher/`. Иконка запуска и эмблема интерфейса — разные ресурсы.
- `sw.js`: `sudak-championship-v13`, network-first для оболочки, предварительный кэш локальной эмблемы/четырёх фото. `data.json` исключён из SW.
- `sudak-data-v1` в localStorage — последний корректный JSON; `sudak-championship-v1` — тур/фильтры/поиск; `sudak-theme` — тема. Есть встроенный резерв данных. Старый ответ CDN не откатывает более новый JSON.
- `scripts/build_pages.py` выбирает свежую совместимую базу из seed, Pages и checkpoint успешной production-публикации. Запускает оба парсера во временной папке, проверяет каждый результат, собирает `_site`.
- `.github/workflows/update.yml` публикует только main, без коммитов данных обратно в Git. Блокировка охватывает всю транзакцию, текущая публикация не отменяется. Checkpoint хранится 90 дней. Ошибка восстановления останавливает публикацию; ошибка парсера оставляет last-good.
- `.github/workflows/check.yml` выполняет Python/Node/браузерные тесты и собирает артефакт без production-deploy. Его `paths` не включает этот Markdown: документационный PR может не запустить check автоматически. Менять workflow ради отчёта не требуется.

## 5. Предлагаемая универсальная архитектура

### 5.1. Единый контракт с совместимостью

Добавить **версионированный опциональный блок `platform` в тот же `data.json`**, сохранив все старые корневые поля и их смысл. Старый клиент игнорирует расширение; новый при его отсутствии работает через legacy-адаптер «Судака». Браузер получает готовый JSON, не парсит РФФК с телефона.

Один снимок сохраняет атомарность, существующий офлайн и защиту от старого CDN. Не вводить 11 обязательных запросов на запуск. Возможное последующее разделение тяжёлых протоколов на версионированные ресурсы — отдельный этап с проверкой офлайна после измерения размера.

Следующая таблица — проект контракта, **не уже реализованные поля**.

| Сущность | Ключи и ответственность |
| --- | --- |
| `platform.schemaVersion` | Версия нового контракта; неизвестную версию нельзя принять как известную |
| `teamsById` | `teamId → {name, city, provider, sourceTeamId, sourceUrl, branding, quality}` |
| `competitionSeasons` | Ключ `4:22`, `competitionId`, `seasonId`, `seasonYear`, 11 `participantTeamIds`, качество отдельных разделов |
| `playersById` | `playerId` из `/players/<id>/`, ФИО/биография/проверенные источники фото; без единственного постоянного клуба |
| `registrations` | `playerId + teamId`, периоды заявки/отзаявки, позиция/номер если опубликованы, источник; несколько периодов допустимы |
| `rosters` | `teamId + competitionId + seasonId`, ссылки на игроков и подтверждения; клубный список отдельно от доказанного сезонного допуска |
| `playerSeasonStats` | `playerId + teamId + competitionId + seasonId`; nullable игры/старты/замены/голы/пенальти/минуты/дисциплина, происхождение каждого показателя |
| `matchesById` | Одна запись для обоих клубов: `matchId`, контекст турнира/сезона/тура, `homeTeamId`, `awayTeamId`, дата/время/зона/стадион, nullable счёт, статус, `sourceMatchId`, URL |
| `protocolsByMatchId` | Составы с playerId, события с teamId/playerId, полнота; при текстовом событии без доказанной личности `playerId:null`, исходная подпись и причина |
| `standings` | Официальный порядок, teamId, опубликованные командные показатели и качество; не пересортировывать равные очки по придуманному правилу |
| `scorerLeaderboard` | Порядок, playerId, числа и `scope`; общий `competition_season` отделён от `team_season`, клубная подпись не распределяет голы |
| `newsById` | ID из `/news/<id>/`, URL, дата публикации, eventDate только при подтверждении, проверенные teamIds/competitionId, архивность |
| `legacyLinks` | Соответствия старых player/match hash-ключей новым ID, без удаления старых ключей |
| `unresolvedSourceRecords` | Исходные записи с неизвестной личностью/контекстом и причиной, вне реестра 11 подтверждённых участников |

`teamId` — строка из §2.2, `playerId` — официальный числовой ID как строка. Название, дата и место в таблице не являются первичными ключами. `competitionId=4`, `seasonId=22`, год 2026 хранятся раздельно.

Существующие внутренние календарные ID матчей сохраняются с явным seasonId в записи. `sourceMatchId` — уникальная связь с протоколом. Перенос даты не меняет личность матча; публикация протокола дополняет её. Если официальный ID тот же, но изменились тур/стороны, нужен проверенный alias/reconciliation, не второй матч. Без официального ID неоднозначные записи не объединяются по похожему имени или одной дате.

### 5.2. Получение связей по ID

1. **Таблица/участники:** брать teamId из `/teams/<id>/` в каждой строке полного сезонного раздела. Не присоединять ID к старому TABLE по тексту в runtime.
2. **Календарь:** `data-team1`, `data-team2`, ID тура, URL протокола; проверять совпадение атрибутов и ссылок.
3. **Состав:** playerId из ссылки строки, teamId из проверенного контекста клубной страницы. Регистрации в профиле имеют ссылки `/teams/<id>/`. Название служит отображению/проверке контекста, не соединению сущностей.
4. **Профиль/рейтинг:** некоторые сезонные группы содержат только текстовую клубную подпись и непрозрачный `data-id`, например `141422`. Формат не документирован; делить его на предполагаемые ID нельзя. Использовать связанные `/matches/<id>/` раскрываемой группы, уже подтверждённые командные ID календаря/протоколов, регистрацию и контекст турнира/сезона. Несколько допустимых групп — отказ от привязки. Если машиночитаемая связь не доказана, поле остаётся неразрешённым. Допустима отдельно проверенная таблица `sourceBindings` для конкретных profileId/группы/сезона с URL и доказательством; автоматический join по названию запрещён.
5. **События:** сокращённое ФИО не даёт ID автоматически. Можно показать подтверждённое событие с подписью, но нельзя открывать случайный профиль/начислять статистику без доказанной личности. Состав протокола используется только при однозначной связи; существующие строгие проверки «Судака» не ослабляются.

Связи по ID предполагают возможность честно оставить неразрешённую связь. Старый строковый рейтинг нельзя мигрировать как набор якобы доказанных клубных итогов.

### 5.3. Качество и отсутствие значений

На уровне независимого раздела и, при смешанной свежести, записи/метрики хранить `status`, `sourceUrl`, `checkedAt`, `lastSuccessAt`, `lastVerifiedAt`, `coverage`, `reason/errorCode`, контекст и версию парсера. `sourcePublishedAt` только если опубликовано источником. Конфликтующие наблюдения сохраняются с URL в журнале проверки, без молчаливого выбора числа.

| Состояние | Основание | Поведение |
| --- | --- | --- |
| `current` | Значение получено сейчас; личность, контекст и согласованность подтверждены | Число с временем проверки, без обещания live-обновления РФФК |
| `stale` | Есть ранее подтверждённое значение, но нового подтверждения нет или источники конфликтуют | Сохранить число/lastVerifiedAt, обозначить давность/конфликт |
| `not_published` | Корректный доступный источник действительно не публикует поле/строку | `null`, «Не опубликовано»; неполный рейтинг не доказывает ноль |
| `temporarily_unavailable` | Сеть/HTTP-ошибка либо непригодный ответ вместо проверяемого источника | Причина и время попытки; сохранённое значение отдельно остаётся stale |

Состояние попытки и свежесть сохранённого значения разделяются: HTTP 503 не уничтожает числа. `checkedAt` не заменяет `lastVerifiedAt`. Непроверенная редакционная актуальность состава/архивной новости не становится current из-за HTTP 200. Для ещё не исследованного поля нужна внутренняя отметка `not_checked`, которую нельзя превращать в «не публикуется».

Охват — `complete`, `partial`, `unknown`, с числом покрытых объектов где возможно. `0` допустим только как явно опубликованный проверенный ноль. `null` — неизвестно; пустой массив при unknown не доказывает отсутствие игроков/событий. Технический счёт не создаёт авторов голов/минуты. Нельзя получать «полные» сезонные итоги из частичных протоколов или суммы рейтинга. Положение/очки берутся из официальной таблицы; форма последних игр помечается как производная подтверждённых матчей.

Старые `stale`, `stats_current`, `verified`, `leaderboard_current`, `stats_as_of` продолжают работать. Адаптер не повышает качество задним числом. Общий `updated` означает версию снимка, не одновременную проверку всех разделов.

### 5.4. Компоненты и оформление

```text
РФФК → существующий цикл + новый импорт → проверки → единый data.json
                                                        ↓
                                      DataStore + LegacySudakAdapter
                                                        ↓
                  Router → ClubContext(teamId, competitionId, seasonId)
                                        ↓
                   ClubPage / PlayerPage / MatchPage / ChampionshipPage
                                        ↓
                TeamLink, TeamBadge, Roster, Stats, Matches, Standing, News
```

Это схема ответственности, не требование сразу разнести весь HTML по модулям. Первые общие функции можно добавить рядом с действующими. Вынос в отдельные JS-файлы — последующий шаг с проверкой доставки оболочки/офлайна, не обязательное условие расширения.

ClubContext передаётся явно, не меняет глобальный «домашний клуб». Один ClubPage включает название/эмблему, положение/командные показатели, состав, профили, завершённые и предстоящие матчи, результаты, новости при подтверждённом источнике. Календарь фильтруется по homeTeamId/awayTeamId, статистика — по полному составному ключу.

Для каждого клуба — ограниченный объект branding: эмблема, акцент и контрастные токены двух тем. Не объявлять угаданные по эмблеме цвета утверждённым стилем. До подтверждения палитры — доступная нейтральная основа, затем проверенные токены. CSS ограничивается контейнером клубной страницы (`data-team-id`), без изменения глобальных переменных главной «Судака». При ошибке эмблемы остаются название и нейтральное обозначение.

Для 141 сохраняются крепость, эмблема, заголовок, темы, меню, карточки и профили. Универсальная модель может питать прежние представления через адаптер. Перенос «Судака» на общий шаблон допускается отдельно с доказанной визуальной эквивалентностью; он не обязателен для добавления остальных клубов.

### 5.5. Навигация, возврат и будущий портал

Сохранить hash-маршрутизацию в `/fk-sudak/`: прямые ссылки работают на Pages без серверных rewrite и смены настроек.

| Маршрут/действие | Проектируемое поведение |
| --- | --- |
| Пустой hash, `#home` | Прежняя главная «Судака» |
| `#team=936&view=overview` | Общая страница; view: overview/squad/matches/stats/news |
| `#teams` | Список 11 подтверждённых участников из раздела чемпионата, без шестой нижней кнопки |
| `#player=rffk-<id>&team=<id>&competition=4&season=22` | Игрок в выбранном клубном/сезонном контексте; старые URL сохраняются |
| `#matchId=<id>` | Общий центр матча; прежний `#match=<legacyKey>` работает через aliases |
| `#portal` | Будущий общий портал; настройка пустого URL не меняет смысл явного `#home` |

Настройка приложения: `defaultLanding={kind:'club', teamId:'141'}`. В будущем `{kind:'championship', competitionId:'4', seasonId:'22'}` меняет только разрешение пустого маршрута, без новой PWA и смены manifest/start URL.

Общий TeamLink(teamId) объединяет название и эмблему в доступную ссылку. Его используют таблица, обе стороны матча и список команд. Ряд таблицы не превращать в единственную click-зону без клавиатуры. Нельзя вкладывать ссылку на клуб в действующую ссылку на всю карточку матча. При будущем добавлении интерактивности выделить отдельные семантические ссылки без визуальных изменений, сохранив переход по счёту/«Подробнее» в матч, и проверить тестом.

History state хранит безопасного внутреннего родителя, scroll/фокус и фильтры. Back/Android Back восстанавливает тур, поиск, клуб и прокрутку в цепочке таблица → клуб → игрок → матч. При прямом открытии без истории — родитель из контекста, затем чемпионат/главная 141. Неизвестный ID показывает состояние и возврат, не выдаёт «Судак» за найденную команду. ID проверяются по реестру, параметры — по разрешённым значениям; внешний URL нельзя принимать как back. Избегать двойного push при hashchange и циклов назад.
