# Platform v1: фундамент данных, этап 2

Основание: [архитектура](architecture.md), PR #29, объединённый 10.11.2026; база кода `8a67cf294559acd5c11b12b61fa3cb78f5a7b8d0`. Ветка реализации — `feature/multi-club-data`. UI, главная «Судака», маршруты, темы, эмблемы/иконки, SW, production-workflow и настройки Pages не меняются. На этом этапе новых клубных страниц нет.

## Контракт

`data.json.platform` — опциональное расширение прежнего JSON. `schemaVersion: 1`, `provider: "rffk"`. Старый клиент продолжает читать прежние поля, полностью игнорируя расширение. Старый JSON без блока остаётся валидным. Присутствующий повреждённый блок или неизвестная версия отклоняются до публикации.

Исполняемый контракт: `scripts/multi_club_schema.py::validate_platform`. ID — строки. Сезон: competitionId `4`, seasonId `22`, seasonYear `2026`; ключ сезона `4:22`. ID источника берётся только из точного официального HTTPS URL без query/fragment. Ключ команды не зависит от названия.

| Структура | Содержание v1 |
| --- | --- |
| `sourceUpdatedAt` | Версия исходного legacy-снимка при проекции; не время подтверждения всех данных. У нового источника таблицы собственные времена |
| `teamsById` | 11 клубов, teamId/sourceTeamId, provider, название, город, официальный URL, branding, quality |
| `competitionSeasons` | Сезон `4:22`, его год/название, 11 participantTeamIds и quality |
| `playersById` | playerId, опубликованное имя, официальный URL профиля, quality |
| `registrations` | Резерв для подтверждённых регистраций: registrationId, playerId/teamId, competitionId/seasonId, registeredAt/releasedAt, quality. Сейчас пуст |
| `rosters` | По записи `4:22:<teamId>` для всех 11 клубов: контекст, playerIds, quality |
| `matchesById` | matchId, competitionId/seasonId/roundId, homeTeamId/awayTeamId, sourceMatchId/URL, дата/время/зона/стадион, nullable счёт, статус, quality |
| `standings` | `4:22`: контекст, rows, quality; строка содержит rank/teamId, played/wins/draws/losses, goalsFor/goalsAgainst/goalDifference/points |
| `playerSeasonStats` | `<playerId>:<teamId>:4:22`: контекст/источник, nullable games/goals/penaltyGoals/minutes/starts/substitutions/yellowCards/secondYellowCards/redCards, quality |
| `protocolsByMatchId` | Связь с матчем/официальным ID, командные стороны, дата/итоговый счёт, lineups, events, eventsComplete, quality |
| `scorerLeaderboard`, `newsById` | Пустые зарезервированные модели. В v1 валидатор запрещает их заполнение без отдельного нового импортера |
| `legacyLinks` | players: прежний rffk-ID → playerId; matches: прежний текстовый hash-ключ → matchId |
| `unresolvedSourceRecords` | teamsById/matchesById с точной копией source record и reason `identity_not_confirmed` |

Регистрации не выводятся из факта участия в протоколе. Совпадение имени не создаёт связь. Имя сохраняется как подпись уже установленной по URL личности.

### Различия полной и прежней таблиц

Полная таблица РФФК и старый краткий блок могут расходиться (Каштан: 17 матчей/51 очко в полной таблице против 16/48 в прежнем снимке). Новый набор хранится только в platform.standings. Старый TABLE интерфейса не перезаписывается и не связывается с ID по названию. Автоматического выравнивания двух представлений в этом этапе нет.

Парсер выбирает именно `.champ_data_table .tour_table`, проверяет заголовок/ссылку турнира 4, сезон 2026/2026, 11 уникальных официальных ID, порядок мест и согласованность чисел. Движение позиции внутри `.place` не принимается за ранг. Неполная ячейка не превращается в 0.

### Что пока не заполнено

- Полные сезонные заявки/регистрации и статистика остальных 10 клубов. Индивидуальные профили сотен игроков не запрашиваются.
- Карточки в playerSeasonStats: все три дисциплинарных поля null. Итоги не вычисляются из неполного набора протоколов.
- Привязка авторов текстовых событий к playerId. У события есть type, sourceLabel, minute, опубликованный running score или null; playerId остаётся null. Нельзя открыть случайный профиль по сокращённому ФИО.
- `teamId` события означает исходную/зачтённую сторону; для автогола это не доказательство клуба автора. Никакие личные итоги из событий не вычисляются.
- Клубные цвета: branding.accent=null. URL эмблем из аудита — метаданные; локальные ресурсы «Судака» и launcher не заменены.
- Общий рейтинг бомбардиров и клубные новости. Существующие championship.scorers/news остаются в старом JSON без изменений, но не копируются как полная клубная статистика.
- Непрозрачные составные data-id статистических групп не разбираются на предполагаемые цифры. Случай 1698 (УОР/«Саки») не создаёт вымышленной клубной суммы.

## Качество и времена

Каждый quality содержит status, coverage, sourceUrl, checkedAt, lastSuccessAt, lastVerifiedAt, reason. Ошибка попытки дополнительно задаёт lastAttemptStatus/errorCode. Последнее подтверждение и последняя попытка разделены.

| status | Значение |
| --- | --- |
| current | Реально полученный и проверенный набор; в этой реализации — успешно загруженная полная таблица |
| stale | Импортированный/сохранённый снимок, новое подтверждение не выполнялось либо источник отказал; прежние числа сохраняются |
| not_published | Источник корректно доступен и подтверждено отсутствие поля; не используется как замена not_checked или ошибки сети |
| temporarily_unavailable | Ошибка сети/HTTP/разметки; если прежних строк нет, набор остаётся неизвестным, а не успешным пустым |
| not_checked | Импорт данного набора ещё не реализован/не выполнялся. Внутренняя пометка из архитектуры, не утверждение об отсутствии данных у РФФК |

Coverage — complete/partial/unknown. Реестр подтверждён аудитом 10.11.2026, но точный момент повторной проверки каждого клуба не выдумывается: checkedAt/lastVerifiedAt там null, reason указывает на аудит. Перенесённые протоколы/личности не получают фиктивное свежее время. У календаря сохраняется метка исходного раздела; у статистики — доступная прежняя метка подтверждения конкретного профильного снимка.

`stats_as_of` старого набора является агрегатной меткой. При stats_current=false время успешного обновления других игроков не продвигает lastVerifiedAt этого игрока. Без stats_current импортёр не принимает новые числа из промежуточной проекции рейтинга вместо профильных показателей. Сохраняются предыдущие подтверждённые числа, без old platform неподтверждённые поля остаются null.

## Обновление и восстановление

1. Прежние fetch_data.py и update_player_stats.py выполняются как раньше во временной папке.
2. fetch_data дополнительно переносит существующий platform через пересоздание старого корня. Это единственное изменение его алгоритма записи; спортивные парсеры не менялись. Оркестратор также умеет восстановить отсутствующий блок после старого производителя.
3. Восстановление принимает старый JSON без platform. Если свежая production-версия ещё без расширения, choose_baseline переносит самый новый известный platform из seed/checkpoint (с учётом версии содержащей его публикации при равной sourceUpdatedAt), сохраняя более новый legacy-корень. Существующий повреждённый блок не игнорируется.
4. После прежних производителей update_platform обновляет проекцию по ID. Без loader сеть не используется. Production-entrypoint передаёт fetch_season: один дополнительный GET закреплённой сезонной страницы, timeout 30 секунд; опрос сотен профилей отсутствует.
5. Таблица принимается независимо: ошибка/HTML 200 с неверной структурой не удаляет прежние строки и lastVerifiedAt. Если старого набора нет — temporarily_unavailable и пустой список с неизвестным охватом.
6. Вся платформа валидируется до принятия. Проверяются 11 участников, ключи/внешние связи, nullable числа, протоколы, aliases, отсутствие потери уже опубликованных сущностей и неразрешённой истории. Некорректное расширение не отменяет успешное обновление старых данных: сохраняется последний корректный блок.
7. Общая версия JSON продвигается существующим механизмом сборки при изменении payload. Кэш профилей «Судака», расписание и production-workflow не меняются.

Размер исходного JSON с расширением — около 653 KB против 254 KB до изменения; ниже существующего предела 5 MB. Реальную квоту localStorage проверяют браузерные сценарии. Новый клиентский код/дополнительная обязательная загрузка не добавлены, данные сохраняются прежним путём. Документирование размера не заменяет проверки на конкретных телефонах.

## Проверки

Новые Python-сценарии: `tests/test_multi_club.py`. Реальная минимальная фикстура полной таблицы: `tests/fixtures/multi-club/standings-2026.html`, без общих новостей/трекеров, с URL и временем получения. Синтетические отказы/искажения применяются только внутри тестов.

Проверяются реестр/сезон, все 113 записей календаря, отказ от join по именам, null/0, отсутствие новых клубных итогов из рейтинга, ID/составы протоколов, старый формат, aliases, реставрация/оба производителя, partial outage, сохранение чисел/времён, неверная схема и потеря данных. Старые Python/Node-тесты сохранены.

`tests/multi-club.browser.cjs` сравнивает PNG видимой области для одинаковых пяти существующих вкладок при legacy JSON и JSON с platform: четыре ширины, две темы. Это 40 пар сравнения: текст, геометрия и вычисленные стили должны совпасть точно; для растра допускается только шум сглаживания до 2 уровней RGB не более чем в 0,1% пикселей. Снимок принимается после двух одинаковых кадров, указатель отведён от элементов. Также проверяются фактическое получение обоих форматов JSON, отсутствие горизонтальной прокрутки и ошибок JS. Сетевые изображения РФФК заблокированы одинаково в обеих версиях. Установка PWA на физическом устройстве этим сравнением не проверяется.

Новый браузерный тест включён только в check.yml. Workflow публикации, его расписание, права и настройки Pages не меняются. Сборка review-артефакта не выполняет production deploy.

Команды:

```sh
python -m unittest discover -s tests -v
node --test tests/*.test.cjs
node tests/multi-club.browser.cjs
```

Полная браузерная регрессия: browser, championship, player-photos, home-dashboard, match-center, tab-transitions, tab-reload, launch-splash, pages-pwa, themes, pwa-launcher. Для pages-pwa используется локальный упакованный артефакт, не production-сайт. Локальная среда — имеющиеся ARM64 Termux Chromium и Playwright, без установки пакетов.

Проверены итоговый diff, прежние корневые значения JSON, неизменность UI/PWA/production-файлов и упаковка сайта. Результаты GitHub Actions указаны в PR. Автоматического merge и production-публикации на этом этапе нет.
