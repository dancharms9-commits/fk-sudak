## Проверка идентичности и регистраций

Клубный парсер выбирает только таблицу «Состав команды». Сотрудники с теми же CSS-классами исключены: у «Каштана» 29 игроков, а не 32 записи вместе с персоналом. ID берутся из точных официальных `/players/<id>/` и `/teams/<id>/` URL. ФИО используются для проверки, что запрошенная карточка соответствует уже установленному ID; совпадение ФИО не объединяет людей.

У профильной группы проверяются точное название чемпионата и сезон 2026/2026. Непрозрачный `data-id` только соединяет заголовок с его списком матчей: он не разбивается на предполагаемые цифры команды/турнира. Команда определяется пересечением участников официальных матчей с известными `sourceMatchId` в платформе. В неоднозначном случае используются опубликованные клубные регистрационные периоды и даты матчей. Неизвестные ID не создают новых участников.

Если известная часть списка матчей однозначно определяет клуб, можно сохранить опубликованный источником агрегат всей группы. `sourceBinding.sourceMatchIds` содержит только известные доказательства, `unresolvedSourceMatchIds` — остальные ссылки. Итоги не вычисляются суммированием неполного списка. Для сезонной регистрации дополнительно требуется реальная строка клубной регистрации и хотя бы один известный матч сезона внутри её периода. Сам факт участия не создаёт вымышленную дату регистрации. Служебные должности (`roleKind: staff`) сохраняются как общие связи, но не используются для футбольных регистраций или определения игрового амплуа. Заявка без опубликованного начала периода не подтверждается как сезонная: исходная общая запись остаётся в данных.

Пример перехода — [Барканов Сергей · 1698](https://rffk-roo.ru/players/1698/): «Саки» — 5 матчей, 6 голов, 445 минут; УОР — 5 матчей, 1 гол, 337 минут. Это две отдельные строки. Кубковая группа и другой сезон не включаются. Общий профиль без клуба предлагает выбрать контекст, а не складывает цифры.

Сохраняются общие клубные регистрации, подтверждённые сезонные регистрации, исторические связи и неподтверждённые списки. Отсутствие даты отзаявки не означает подтверждённое действующее членство. Исторической связь становится лишь при явно опубликованном окончании всех её периодов до 2026 года. В текущих десяти общих клубных списках таких отдельных записей нет; обработка проверена фикстурами.

## Обновление и сохранение последних данных

Новый `scripts/multi_club_rosters.py` включён последним необязательным шагом в существующий `scripts/build_pages.py`. Прежние спортивные парсеры «Судака» не менялись. В обычной сборке максимум два параллельных запроса, 24 профиля на проход, общий бюджет 120 секунд, тайм-аут запроса до 8 секунд, один повтор для временных ошибок. У клубов и профилей TTL 24 часа; приоритет у давно проверенных профилей. Отсчёт сетевого бюджета начинается при первом запросе, после выполнения прежних парсеров.

Ошибка сети, HTTP или структуры не означает отсутствия состава: последние ID, числа и `lastVerifiedAt` сохраняются, меняется состояние попытки. Подозрительно усечённый клубный список отклоняется. Исчезновение из общего списка отмечается `currentlyListed=false`, без придуманной даты отзаявки. Отсутствующие при новой проверке поля/регистрации сохраняются как `stale`; необязательный `fieldQuality` разделяет актуальность показателей; в прежних строках без него действует `quality` всей записи. Старые необогащённые JSON по-прежнему допустимы. При восстановлении из production/checkpoint независимые составы и профили из seed объединяются по ID и времени подтверждения: более новая ревизия старого корня не удаляет обогащение. Числа сохраняются по полям, таблица — по времени её проверки; свежие данные прежнего производителя «Судака» остаются основой. `sourceUpdatedAt` ранжирует версии футбольного корня, а `updated` — общую публикацию: обогащение платформы не делает старую копию «Судака» новее production. Метаданные без успешного изменения прежнего производителя не продвигают версию его данных; более свежий футбольный снимок принимается даже после более поздней публикации расширения.

Массовый сбор на телефоне не выполнялся. Основная загрузка выполнялась только в отдельном GitHub Actions [аудите](https://github.com/dancharms9-commits/fk-sudak/actions/runs/42778384573), затем уточнялась [85 запросами](https://github.com/dancharms9-commits/fk-sudak/actions/runs/42780181745) и [16 запросами](https://github.com/dancharms9-commits/fk-sudak/actions/runs/42803072723). Последняя проверка — 10.11.2026 10:54:48 UTC. Workflow `roster-audit.yml` запускает ограниченный сбор лишь для PR из этого репозитория с явно установленной меткой `rffk-data-audit`; права только чтения, результат — review-артефакт. Метка после проверки снята. Этот workflow не публикует сайт. Клиент не загружает HTML профилей и не выполняет сбор при запуске.

## Интерфейс и совместимость

Используется тот же `renderPlayer`, что и для футболистов «Судака». Контекстный маршрут: `#player=rffk-146&team=936&competition=4&season=22&from=team`. Старые `#player=rffk-202...` продолжают открывать прежний профиль с голами по протоколам. `#team=141` ведёт на существующую главную.

В клубном составе сначала показаны подтверждённые участники, отдельно раскрываются общий неподтверждённый список и история. Амплуа берутся из источника; номера отображаются только опубликованные. Фото — официальный URL с ленивой загрузкой, без base64; при сетевой ошибке остаются инициалы. Из профиля доступны клуб, другие подтверждённые связи и официальный источник. Возврат восстанавливает историю, прокрутку и фокус; прямые ссылки и обновление страницы поддерживаются. Пять кнопок нижней навигации сохранены.

Все прежние футбольные корневые значения `data.json` совпадают с `main`. Меняется только `platform` и общая ревизия `updated`, чтобы существующий клиент принял расширенный снимок; она не объявляет старые спортивные данные свежими. SW, manifest, PWA-иконки, эмблема/фотография/заголовок «Судака», CSS главной и production-workflow не изменялись.
