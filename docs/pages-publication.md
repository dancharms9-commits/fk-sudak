# Публикация ФК «Судак» через GitHub Actions

## Причина и границы изменения

Раньше `update.yml` раз в час коммитил `data.json` и
`player_stats_cache_2026.json` в `main`. Изменялся в том числе `updated`.
Рабочие ветки содержали другой снимок тех же файлов, поэтому Git требовал
разрешать конфликты при объединении функциональных PR.

Теперь `main` хранит исходники и проверенный исходный снимок данных для тестов
и восстановления. Почасовые данные существуют в опубликованном сайте и
артефактах Actions; они не возвращаются в Git. Отдельная ветка или репозиторий
для данных не нужны. Существующие JSON не удалены и не изменены этим переходом.

Дизайн, HTML, CSS, фотографии, manifest и Service Worker не меняются.
Адрес остаётся https://dancharms9-commits.github.io/fk-sudak/ .

## Как работает публикация

`.github/workflows/update.yml` запускается по прежнему расписанию `0 * * * *`,
при `push` в `main` и вручную через **Run workflow**. Публикация разрешена только
из `main`. Workflow имеет `contents: read`, без команд `git commit`/`git push`.

1. Проверяет источник Pages через API, ничего не переключая. Пока источник
   `legacy`, выводит инструкцию и оставляет действующий сайт без изменений.
2. Получает текущий `main`, включая при отложенном запуске или повторном запуске
   старого задания. Учётные данные checkout не сохраняются.
3. Получает опубликованный `data.json` с уникальным URL и `Cache-Control: no-cache`.
   Три неудачные попытки останавливают публикацию: старый сайт продолжает работать.
4. Находит свежий резервный артефакт `football-state-<run_id>-<attempt>` из успешной
   производственной публикации этого workflow. Исключает PR, чужие ветки, неудачные
   и отменённые запуски. Учитывает страницы API и повторные запуски старых заданий.
   Ошибка API/повреждённый резервный файл останавливают публикацию, чтобы не принять
   устаревший ответ CDN. При первом переходе артефакта ещё нет — используется сайт.
5. Выбирает наиболее свежий корректный снимок из сайта, резервного артефакта и
   исходного снимка. Более новый снимок не может потерять опубликованные сущности.
6. Во временном каталоге запускает существующие `fetch_data.py`, затем
   `update_player_stats.py`. Кэш статистики восстанавливается из актуального JSON,
   а не из старого кэша в `main`. Каждый результат проходит проверку перед принятием.
7. Собирает `_site` с приложением, всеми ресурсами и проверенным JSON. У изменённого
   итогового JSON всегда новая метка `updated`, даже при обновлении статистики
   в пределах той же минуты. Если данные не изменились, метка сохраняется.
8. Загружает Pages artifact и резервный снимок, затем выполняет `deploy-pages`.
   Резервный снимок считается пригодным для восстановления только после успешного
   завершения всего запуска. Срок хранения резервных артефактов — 90 дней;
   опубликованный сайт остаётся основным постоянным хранилищем.

Общий `concurrency` охватывает **получение → парсинг → упаковку → публикацию**,
а не только последний шаг. `cancel-in-progress: false` позволяет текущей
публикации закончиться до начала следующей. Ожидающие устаревшие задания могут
заменяться новыми по правилам GitHub; начавшееся задание всё равно получает текущий
`main` и последнюю публикацию. Новые и старые сборки не публикуются параллельно.

## Недоступность или неполный ответ РФФК

Проверяется синтаксис JSON, сезон, дата версии, таблица, результаты, состав,
профили и подтверждённые поля статистики, протоколы, команды, туры, матчи и
бомбардиры чемпионата. Потеря уже опубликованных игроков, доступных протоколов,
матчей или туров отклоняет новый снимок. Это защищает и от HTML-страницы ошибки,
которую сервер ошибочно вернул с кодом 200. NaN/Infinity также запрещены.

Ошибка, тайм-аут или некорректный результат основного парсера сохраняет последний
корректный снимок; дополнительный парсер всё ещё может получить статистику.
Ошибка дополнительного парсера сохраняет проверенный результат основного.
Существующая независимая обработка источников чемпионата и пометка `stale`
сохраняются. Новый код приложения можно опубликовать вместе с сохранёнными данными.
Если не удалось надёжно восстановить исходное состояние с Pages/API, публикация
вообще не начинается. Ошибка загрузки артефактов также не запускает deploy.

Намеренное удаление игрока/исторического матча или смена сезона требуют отдельного
изменения правил и исходного снимка в PR; неполный ответ источника не должен
выполнять такую миграцию автоматически.

## PWA, кэши и офлайн

Прежняя загрузка `data.json?v=<Date.now()>` с `cache: no-store` сохраняется.
Service Worker обходит `data.json`, поэтому его кэш не удерживает старые данные.
Открытое приложение проверяет сайт раз в пять минут, при возврате на вкладку,
фокусе и восстановлении сети. Более старая метка `updated` не откатывает
показанные данные. Корректный JSON сохраняется в `localStorage` под прежним
ключом `sudak-data-v1`; при отсутствии сети восстанавливается вместе с кэшированной
оболочкой и фотографиями. URL, scope, manifest и ключ хранилища прежние,
переустановка PWA для этого перехода не требуется.

## Безопасное включение владельцем репозитория

До объединения PR настройки Pages **не менять**.

1. Дождаться успешного задания **Проверки приложения / check** в PR. Оно запускает
   Python, Node и браузерные тесты, собирает сайт и загружает Pages artifact для
   проверки, но не имеет шага публикации.
2. Объединить PR в `main`. Старый бот после этого больше не коммитит данные.
   Если источник Pages ещё `Deploy from a branch`, новый workflow только выведет
   инструкцию. Текущий сайт остаётся доступен; переход лучше завершить сразу.
3. Открыть **Settings → Pages → Build and deployment → Source**, выбрать
   **GitHub Actions**. Ветку, адрес сайта и домен менять не нужно.
4. Открыть **Actions → Обновление данных и публикация Pages → Run workflow**,
   выбрать ветку **main**, нажать **Run workflow**.
5. Дождаться успеха `publish`, проверить приложение и следующую почасовую
   публикацию. В истории `main` не должно появиться новых бот-коммитов данных.

Отдельные PAT/секреты не нужны: достаточно встроенного `GITHUB_TOKEN`.
Не запускайте старые исторические версии workflow с записью в Git.
Для отката кода используйте обычный revert через PR: текущие данные при следующей
публикации восстановятся с сайта, а не из старого коммита. Не возвращайте прежний
workflow с бот-коммитами.

## Проверки

```sh
python -m pip install requests beautifulsoup4 pyyaml
python -m unittest discover -s tests -v
node --test tests/*.test.cjs
# Для браузерных проверок — Playwright и Chromium из check.yml.
node tests/browser.cjs
node tests/championship.browser.cjs
node tests/player-photos.browser.cjs
node tests/home-dashboard.browser.cjs
node tests/match-center.browser.cjs
node tests/tab-transitions.browser.cjs
node tests/tab-reload.browser.cjs
node tests/launch-splash.browser.cjs
# После сборки _site:
node tests/pages-pwa.browser.cjs
```

`test_pages_build.py` проверяет ошибки восстановления/парсинга, сохранность данных,
восстановление кэша, версии обновлений, ограничения прав и конфигурацию сериализации.
`pages-pwa.browser.cjs` работает с упакованным сайтом в `/fk-sudak/`: сервер намеренно
отдаёт JSON с большим `max-age`, затем меняет данные при неизменном SW. Проверяются
пятиминутный опрос без ожидания реальных пяти минут, отсутствие перезагрузки,
сохранение фильтров, защита от старого ответа/503, офлайн-перезагрузка с 16 протоколами,
41 профилем, 22 турами и фотографиями, затем возврат сети.

Полноценная производственная публикация и реальный почасовой триггер новой схемы
проверяются после объединения и включения Source: GitHub Actions. До этого
проверяются сборка с реальным РФФК, артефакт и поведение в настоящем Chromium;
действующий сайт не используется как испытательный стенд.

Документация GitHub: [Pages с собственным workflow](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages),
[управление параллельными запусками](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency).
